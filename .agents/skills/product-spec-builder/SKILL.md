# Product Spec Builder (Antigravity 专版)

[任务]
    **0-1 模式**：从模糊想法到首版 Spec。AI 不天然懂用户的行业、组织、历史和隐性规则，先向用户学这门生意，再用用户自己的案例把学到的讲回去，直到用户挑不出错；共同形成目标行为与可验收的 `Product-Spec.md`。
    **迭代模式**：承接已学到的业务含义，区分“新增需求”与“原先理解错误”；只修订受影响的规格，记录 `Product-Spec-CHANGELOG.md`，并执行**纠正传播（Correction Propagation）**，把纠正传给后续架构、设计、计划和验收，撤销旧假设对下游的毒害。

[依赖检测]
    Skill 启动时第一步自动执行。
    - 0-1 模式无前置文档要求。
    - 迭代模式读取既有 `Product-Spec.md` 与变更历史；若不存在则回退至 0-1 模式。
    - 局部需求足够支持局部工作，不强求整份全量定稿。没有材料不等于没有上下文。

[五条底线]
    1. **四种话分开标**：
       - 用户确认的事实 `[确认]`
       - AI 的逻辑推断 `[推断]`
       - AI 采用的低风险最佳实践 `[默认]`（用户行使否决权）
       - 尚未弄清的关键未知 `[待定]`
       在对话里分开说，在 Spec 里逐条分开标，每条带来源。没标的一律按推断对待。两条要求冲突时，单列“矛盾”摆给用户选，严禁自己圆场。AI 的建议单独标“建议”，不混进需求。
    2. **问过的绝不再问**：
       Spec 末尾“澄清记录”保存每次问与答；用户已回答、已授权、已明确委托的事，本 Skill 与后续任何阶段都不重问。仅在出现与原答案直接冲突的新事实时，摆出矛盾再问。
    3. **问题有成本（严格预算）**：
       只问会改变“代码要写什么”或“怎么验收”的问题。事实归自己查，决定才问人——代码、数据库、旧文档能查到的，查完写明来源，不拿去打扰用户。每个问题带一个推荐答案，用户一个字就能答。
    4. **引导不指路，价值优先**：
       把用户的想法拉出来，不把自己的偏好塞进去。不默认给功能加 AI；用户提出 AI 需求或存在明确替代人脑判断的场景才评估，提的时候说清替代哪一步、错了谁兜底。
    5. **先问是地基还是锦上添花**：
       核心数据与基本流程未稳前，报表、大屏、看板类需求默认降级挂账；含重计算的条目在签字前附实测成本预估，拿不到就进待定表。

[交互深度分档]
    先判档再开口，判据是“不确定程度 × 做错的代价”：
    - **直推档**：边界清楚、错了一改就好（改文案、加选项、换默认）。不问，改完一句话复述。
    - **确认档**：AI 能推断但会改变行为。给出推断 + 推荐 + 1 个问题，用户一个字能答。一次最多两问。
    - **探索档**：为什么做、谁受益、现在怎么干、例外在哪有一样说不清，且做错代价高。进入 [向人学业务]。提问预算：自用/小工具 6-8 问，内部系统 8-12 问，对外或涉钱涉合规最多 15 问。
    - **委托档**：用户说“你定”“按经验来”——AI 自主决策，记入“决策依据”并标 `AI 决定（用户委托）`，后续不回头问。

[向人学业务（四条线）]
    一次只拉一条线，每条问到能用一个具体案例复述为止。问的是“上一次发生的事”，不是“一般来说”：
    1. **现在怎么干（as-is 故事）**：
       真实发生过的一次，谁接手、看了什么、怎样判断、交给谁、怎么知道结束。听到手工传递、重复录入、来回确认，记为核心价值候选。
    2. **为什么做、谁受益谁受损**：
       谁在为现状买单（时间、钱、风险）；做成了谁变好，谁可能变差。受损者往往是隐性规则的来源（如财务必须要看到原始纸质单号）。
    3. **规则与例外**：
       每条规则要一个例子和一个例外。“有没有哪次不是这样处理的？那次为什么？”例外比规则更能暴露真实边界。
    4. **谁说了算与历史**：
       以前试过没有？上次卡在哪？哪些决定已经定了不能碰？谁能拍板？

[从任务收敛到完整结果]
    - **把价值与代理指标分开**：人完成了什么业务目标才叫完成，点击量或页面时延只是代理指标。
    - **最小范围保留结果链**：任务目的 → 操作对象 → 动作与输入 → 判断规则 → 事实变化/输出去向 → 可见反馈 → 退出或恢复。
    - **区分对象、意图与状态**：实体不直接套 CRUD，重复操作按业务意图去重，请求超时不等于服务端失败。

[需求产物深度（requirementsDepth）]
    - `research`：交付问题、已有事实、证据与未知项，不称可开发规格。
    - `brief`：写清目标、范围、关键行为、验收与约束（短说明）。
    - `structured`：按功能与流程组织需求，补齐受影响的输入输出、错误/边界与验收条件。
    - `formal`：在 structured 基础上给需求稳定标识（`REQ-xxx` / `NFR-xxx`），明确公共契约、失败行为、可追踪验收与适用质量属性。

[纠正传播（Correction Propagation）]
    用户指出理解偏差或变更需求时：
    1. 先复述修正后的业务含义，指出原解释会造成的具体代码与逻辑错误；
    2. 区分是“用户变更需求”还是“AI 理解错误”，不把 AI 误解转嫁为用户加需求；
    3. 逆向追踪受影响的架构边界、质量目标、界面文案/状态、DEV-PLAN Task 与已写用例；
    4. 将修正就地同步至权威文档；受影响的旧完成记录标记“旧结论失效”，由主 Agent 重新安排对应角色修正。

[工作流程]
    1. **加载与识别**：读取已有规格与变更；确认是 0-1 学习、目标行为选择还是修订。
    2. **完善与决策**：按交互深度与四条线开展澄清；执行 [spec-self-review] 单元自检。
    3. **写入产物**：
       - 新建：按 `templates/product-spec-template.md` 输出 `Product-Spec.md`。
       - 变更：更新 `Product-Spec.md` 并在 `Product-Spec-CHANGELOG.md` 中按 `templates/changelog-template.md` 记录版本、差异与纠正原因。
    4. **同步记忆**：将关键决策（Decisions 三要素：依据、适用范围、取代哪条）写入 `progress.md`。
    5. **交接后续**：规格就绪后引导至架构设计（`/arch-designer`）、DFX分析（`/dfx-designer`）或界面设计（`/design-brief-builder`）。
