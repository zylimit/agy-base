# DEV-PLAN 输出模板

没有既有计划时默认输出 `DEV-PLAN.md`，供 dev-builder 执行；已有载体沿用实际路径与结构。按 Skill 正文的 `requirementsDepth` 和实际范围裁剪：一条完整 Task 足够时不增加 Phase；有多组交付或复杂依赖时再分组。research 只输出研究结论与缺口，不把未知执行条件写成 ready。

下面的括号是填写提示。可派发 Task 必须具体；未知项写明阻塞条件与解决方式，可以引用稳定契约，不靠删除 TODO 等词语假装计划就绪。

```markdown
# Development Plan — [项目名称]

关联：[实际 PRD/Spec 的版本/需求位置或已确认会话决定；已有架构、DFX 或设计资料仅列适用项]
范围：[此次交付行为及明确非目标]
状态：[可执行 / 部分可执行及阻塞项 / 研究中]

## Task 1：[交付行为]

- Requirements：[适用的正式 REQ/NFR ID；放在 Task 标题直属内容中。项目无正式编号时删去此字段，沿用实际来源，不为检查造 ID]
- 目标：[可观察行为；formal 深度补需求引用、公共契约与失败条件]
- Business context：[目标参与者、关键规则与实际来源、一个有区分力的输入输出例子、未决项及影响；可并入目标/现有模式，纯内部维护注明适用的工程契约即可]
- 文件范围：[项目内具体相对路径及各自职责，包含需要修改的测试、配置文件]
- 边界与责任：[owner、沿用的现有模式及本 Task 特有的非目标；全计划共用事实可引用]
- 前置依赖：[已具备的条件 / 必须完成的 Task；包括实际需要的共享契约、隔离初态与验证入口，无依赖则写无]
- Assurance 输入：taskId=`[稳定 ID]`；operation=`develop`（验收前转 `complete`）；paths=`[同文件范围]`；intrinsicRisk=`[low|medium|high]`；impact=`[实际影响类别]`；attributes=`[适用属性]`
- 聚焦验证命令：`[仓库已有或本 Task 将提供的具体命令，注明工作目录与必要输入；说明风险/P0–P2、有效层次、已知耗时及证据产生者。先受影响反馈，最终冻结后由 controls 要求的角色运行必要完整 gate；不重复已有相同绑定的新鲜证据]`
- 预期结果：[退出状态、实际观察入口及行为断言，以及需保持的原行为；关键预期关联来源与业务例子，DFX 目标使用其测量条件；不要把计划命令写成已通过]
- 阻塞条件：[仅有未决项时保留；说明影响、解除依据与负责处理的 Task]

## 技术依据（按需）

已有环境可用一段话列清单、版本和验证入口；需要比较多项技术时用表格：

| 技术/工具 | 当前版本或约束 | 核验依据 | 本次决策 |
|-----------|----------------|----------|----------|
| [适用项] | [项目版本/约束] | [清单、lockfile、实际命令，或官方来源与日期] | [复用/经授权变更及理由] |

## 设计与数据变更（按需）

[引用适用的架构、DFX、UI 或数据契约；无需新增设计时不创建此节。涉及数据库时列真实表/迁移、所属 Task 与用途。]

## 风险与未决事项（如有）

[具体条件、受影响 Task、已查依据与解除方式；已确定部分可继续，未决部分不标为 ready。研究 Task 写需区分的解释、取证方法和退出条件，不预设验证一定成功；结论说明支持的后续决定及未验证范围，不把实验成功计为生产完成。]

## 理解纠正与后续影响（发生时）

[修正后的含义与来源 → 被替代的旧解释 → 受影响需求/设计/Task/验收 → 当前处置。保留完成历史并注明对当前要求的适用性；旧实现要改时新增修正 Task，由主 Agent 通知正在执行的角色。]

## 开发规则

- 主 Agent 在 Task 开始、恢复及 operation 转换前，只用 Task 的 Assurance 输入请求 resolver，并传入完整 resolved block；执行者消费 target/execution controls
- Business context 仅是 Markdown 交接内容，不写入封闭 task-state JSON；关键规则和预期来源随派单传递，不能靠文件指针猜测
- review、测试新增、验证广度、独立 tester 和证据等级由 resolved controls 决定；用户显式要求的 test/review/check 必须执行
- 测试比例按项目/可独立交付组件总存量口径核对，不给单个 Task 凑用例；套件分级、owner 与老化复核沿既有目录/计划，只有适用维护项才列入当前范围
- reviewRounds 是上限，首审覆盖全部必要 lens；修正后复核修复和影响，APPROVE 即停。到上限仍有阻断项时交回最小修复/范围选择与未完成事实，不重置轮次
- SKIPPED 仅用于平台确实不适用，DEFERRED 仅用于 Rapid evidence debt；二者均非 PASS
- 不自动 commit；commit/push 是与质量结论分离的显式授权动作
- 已有包管理器及版本：[仅适用时填写，不为计划新增依赖]
```

## 写作要点

采用正式编号时，`plan lint` 可核对 Task 直属 Requirements，或所选章节直属的 `Task | Requirements/需求` 表。局部计划显式传本次 `--requirements`，包含历史章节时用 `--section` 精确圈定；Spec/Plan 沿用真实路径，保存后的完整命令见 [主流程第 5 步](../SKILL.md)。风险段、普通提及与围栏内的编号不是已排 Task；该检查只证明格式覆盖，不替代下列业务校准。

1. **粒度与顺序**：Task 数量由独立验收、依赖和 owner 边界决定。需要 Phase 时，按业务切片组织可体验结果；基础设施 Task 说明支持哪个切片及自身验收。不凑固定数量，不把基础设施、i18n 或部署列为必经阶段。
2. **完整范围**：保留目标与业务依据、文件职责/owner、前置依赖、六项 Assurance 输入、验证及有来源的预期；测试、配置和文档路径与生产文件同样按实际改动列出。共用契约可引用并带必要语义，不重复填充全文。
3. **适用验证**：使用该交付物真实存在或计划提供的检查。CLI 验证输出与退出码，文档/配置验证对应契约，具有构建或启动步骤的产品才列相关命令；命令尚缺时安排提供它的 Task 或标明阻塞，不虚构通过结果。
4. **技术证据**：无选型/API/依赖变化的已知环境用本地清单和版本证据；涉及当前外部能力、依赖决策或不确定兼容时按正文查官方资料。记录实际版本，不填 `latest` 或默认升级。
5. **按需设计**：UI、数据库、架构/DFX 表格只在需求与 controls 适用时保留；非 UI 不要求 Design Brief、页面结构或视觉下一步。formal 深度仍需需求、公共契约与失败条件追踪，可引用已确认文档。
6. **就绪状态**：区分可执行工作与具体阻塞项；只有验证后才填写实际完成证据，计划中的验证命令不是 PASS。
7. **纠正传播**：用户新增范围与 Agent 理解错误分开记录。更新原有 Task 的业务依据、依赖和验收，保留旧记录的历史和替代关系；不让新需求段落与旧预期同时指导实现。
8. **验收落地**：需要跨边界、共享契约或研究任务时，使用 [验收与依赖方法](../references/acceptance-and-dependencies.md)。在既有字段说明每个结果如何产生、谁消费、哪些前提未具备；单一明确修订只填适用内容，不拆固定阶段。
