# 精益工程与五大避免过度防线 (Lean Engineering Guardrails)

在全生命周期的代码编写、测试、审查与发布过程中，必须严格遵循以下五项核心防线，消除 AI Agent 常见的虚荣、自大与膨胀行为：

---

## 1. 坚决避免过度设计 (Avoid Over-Engineering)
- **YAGNI（You Aren't Gonna Need It）**：只实现当前 Spec 和当前 Task 明确规定的逻辑。
- **严禁预留假想抽象**：绝不为了假想的“未来扩展”增加未经授权的抽象层、通用包装（Wrapper）、万能工厂类（Factory）或未被要求的插件总线。
- **真重复才提取，规则不同绝不硬合**：只有当两处以上代码逻辑 100% 相同且变化原因相同时才成组抽离；若只是外观长得像但业务规则不同，坚决不强行合并。
- **保持接口极简**：窄接口优先，内部实现细节绝不向外暴露。

---

## 2. 坚决避免过度测试 (Avoid Over-Testing)
- **破除覆盖率虚荣**：拒绝机械盲目的 100% 代码覆盖率追求。不测简单的 Getter/Setter、纯数据传输对象（DTO）和第三方库的原生行为。
- **风险分级预算（P0 / P1 / P2）**：
  - **P0（核心高后果）**：权限、状态机迁移、数据一致性。必须具备高强度独立断言与契约测试。
  - **P1（主业务分支）**：常规校验、核心流程。
  - **P2（长尾边缘）**：低频提示、偶发日志。
- **严防镜像测试陷阱（Mirror-Image Trap）**：测试作者绝不能根据刚刚写好的生产代码“反推”断言值；预期值（Expected）必须直接来源于业务需求规则或独立 Fixture。
- **用例生命周期与老化退休**：建立套件维护机制，长期绿（如连续 20 次执行无一失败）且不具备核心保护属性的用例进入候选退休队列。但**密钥管理、危险命令拦截、安装器、发版装配四类安全底线用例永不退休**。

---

## 3. 坚决避免过度检视 (Avoid Over-Reviewing)
- **首审一次覆盖，单轮集中收敛**：首审必须一次性覆盖功能、架构与 5-D DFX 全量视角，集中给出有确凿证据的实质问题，严禁拆分成多轮零碎找茬。
- **严格区分阻断与非阻断**：
  - **Blocker / High（阻断）**：破坏业务规则、数据丢失、越权、死锁、崩溃。必须修复并由原审查者针对修复复核。
  - **Medium / Low / nit（非阻断）**：命名偏好、个人排版风格、可选重构。标记为建议，**绝不阻断 APPROVE 放行**。
- **审查轮次硬上限（reviewRounds ≤ 2）**：APPROVE 即刻收口，同一争议绝不反复换人投票，严禁陷入无限拉锯。

---

## 4. 坚决避免过度防御 (Avoid Over-Defending)
- **Fail-Visible，拒绝静默吞异常**：严禁空 `catch {}`、严禁无脑 `try-catch` 后默认返回 null/false、严禁静默重试。未预期异常必须显性暴露，让调用者立刻感知并报错。
- **边界防御，内部信任**：在系统外围入口（用户输入、外部网络响应、文件系统读取）执行严格校验；系统内部模块调用保持类型契约信任，不写层层包裹的判空裹脚布代码。
- **FMEA 真实故障隔离**：仅在跨微服务或关键外部依赖处设计熔断与降级，内部逻辑保持干净直白。

---

## 5. 坚决避免过度可信 (Avoid Over-Trusting)
- **零盲信原则**：Subagent 口头自报的“我已完成”、“测试全绿”没有任何公信力。
- **客观凭据为唯一真理**：结论必须绑定当前 exact commit/diff hash，且必须附带测试运行器真实的 `exit code 0` 与通过明细。
- **红测锁定缺陷 (Red-Locks-The-Bug)**：修 Bug 必须先由独立 `tester` 写出复现失败的红测（主 Agent 亲眼查验红灯），修复使红测转绿才算成功。
- **写测独立性**：`implementer` 与 `tester` 必须分属不同 Fresh 实例，严禁自测自签。
- **发布现场探针**：构建成功 ≠ 系统存活；发布上线必须独立查验真实进程/容器启动时间戳与 HTTP `/healthz` 冒烟探针。
